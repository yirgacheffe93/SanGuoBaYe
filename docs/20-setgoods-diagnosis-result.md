# 20 · SetGoods 定位结果：U8 反射视图被当成 U16 队列

> 2026-10-26，执行文档 19 的取证与定位阶段。根因已确认；本轮没有修改游戏规则或重导内容。证据：`docs/evidence/setgoods-diagnosis.json`。

## 1. 结论

生产 WASM 正常执行 `SetGoods`，设置 `0x8000`，与同源 C 的预期一致。原先所谓“生产队列未变化”，实际是读取了 U16 的低字节。

`g_GoodsQueue` 的生产反射元数据为 U8 字节数组：`type=0`、`elementBytes=1`、`length=2000`、基址 `2647568`。生产消费者使用 `base + queueIndex * 2`、`i32.load16_u` 和 `i32.store16`。反射 getter 按元数据读取字节本身没有矛盾，错误在于观测工具和导入器将字节索引当成了道具队列项索引。

正确读取方式：

```js
const address = goodsQueue._addr + queueIndex * 2;
const raw = new DataView(Module.HEAPU8.buffer).getUint16(address, true);
const toolIndex = raw & 0x7fff;
const discovered = (raw & 0x8000) !== 0;
```

每次读取重新取得当前内存视图，做地址与容量检查。写受控测试数据时同样按 U16LE 写入，不能用 U8 getter/setter 代替队列项操作。

## 2. 两个场景的证据

| 场景 | 命令执行前 U16 | 完成后原始字节 | 完成后 U16 | 旧反射读值 | S4 RNG |
|---|---|---|---|---|---|
| A：平原、关羽、注入方天画戟 | `[0]` | `[0, 128]` | `[32768]` | `[0]` | 679304702 |
| B：北平、公孙瓒、原始太玄兵符 | `[31]` | `[31, 128]` | `[32799]` | `[31]` | 1008917062 |

每个场景分别运行玩家无断点、非玩家无断点、玩家有断点三次，共六次。都验证：候选前队列正确，执行者已从城市移除；S4 命令槽为 255、执行者归队；金粮不变；S5 月度更新后发现位仍存在。非玩家对照只改变玩家君主，执行者和目标道具不变。

有断点样本额外记录：

- `0x47b4`：实际候选分别为 0、31，执行者分别为 89、16，运行时 `bole=0`，且直接从条件内存读取相同结果。
- `0x484b` / `0x485d`：进入报告与报告返回。返回时仍未写发现位，符合源码顺序；Asyncify 重入同一调用点的暂停次数单独计数，不代表多次搜寻。
- `0x4894`：进入内联的 `SetGoods` 遍历。
- `0x48dc`：即将执行 `i32.store16`。A 地址 `2647574`、值 `32768`；B 地址 `2647568`、值 `32799`。均与城市队列项计算地址相同。
- `0x48df`：写入后的相同地址读出预期 U16 值。

因此，调用条件、写入地址、实际写入、命令完成和月度后状态已形成闭环。无需重编译 C，也无需增加生产 WASM 导出入口。直接调用 `SetGoods` 的实验不再是确定本次根因的必要条件。

例如 190 年许昌 `ToolQueue=7`、`Tools=3`：


此前用许昌证明“重复道具已保留”的依据失效。这不意味着规则可以去重；真实重复项仍须保留，重复行为应使用明确构造的样本及后续生产验证。

现有检查把错误的 `_rawToolQueue` 与其派生的 `toolEntries/toolIds` 相互比较，所以顺序、重复和高位检查仍然通过。`node tools/main-import/import.mjs --check` 此时通过，只能证明重现相同输出。后续应增加独立字节解码对照，以及写入 `0x8000/0x801f` 后仍能读回完整 U16 的受控检查。

人物队列的生产反射元数据为 `type=1`、元素宽度 2，当前使用的元素索引与生产 U16 一致。本次未发现人物队列具有相同问题；不据此推断全部反射字段均已审计。
