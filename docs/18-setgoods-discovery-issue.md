# 18 · 道具发现位问题：前因、证据与待定位项

> 状态：根因已确认并修复。`20-setgoods-diagnosis-result.md` 证明生产正常写入高位，旧工具误读 U8/U16；导入、C# 提交、防重复、golden、存档和独立应用验收现已完成。本文保留排查历史，当前结论见 `17-main-m2b.md`。

## 1. 问题摘要

在 main 的道具搜寻规则中，同源 C 预期：找到道具后，把城市道具队列对应项的 `0x8000` 发现位设为 1，避免以后重复发现。

但生产 WASM 的两个实际场景中，搜寻路径和 RNG 均正确，队列却没有出现这个高位变化：

- 预期 `[0] → [32768]`，实际 `[0] → [0]`。
- 预期 `[31] → [32799]`，实际 `[31] → [31]`。

因此，当前不能同时声称“已经发现道具”和“发现状态已与 main 完全对齐”，也不能可靠实现防重复发现。

## 2. 为什么会走到这里

项目按 main 重写时，M2A 只实现了搜寻的金钱分支。M2B 开始补齐人物、道具和其他分支：

1. 同源 C 显示道具搜寻成功后调用 `SetGoods(city, goods)`。
2. `SetGoods` 应遍历城市道具队列，找到同 ID 且未发现的项目，并设置 `0x8000`。
3. 导入器已经保留原始队列顺序、重复道具和高位。
4. 在生产 WASM 做 golden 时，发现 RNG 正确但队列发现位没有变化。
5. 因此 M2B 的道具发现功能被单独列为未解决项，没有按预期强行写成已通过。

相关 main 源码：

- `citycmd.c:223`：道具分支调用 `SetGoods(Order->City, p)`。
- `infdeal.c:680`：`SetGoods` 的实现。

## 3. 同源 C 的预期行为

`SetGoods` 的核心逻辑是：

```c
for (i = city.ToolQueue; i < city.ToolQueue + city.Tools; i++) {
    if ((g_GoodsQueue[i] & 0x7fff) == goods && !(g_GoodsQueue[i] & 0x8000)) {
        g_GoodsQueue[i] |= 0x8000;
        break;
    }
}
```

也就是说：

- `0x7fff` 保存实际道具索引。
- `0x8000` 保存“已发现”状态。
- 队列项而不是全局道具保存发现状态，所以不同城市、重复道具可以独立处理。

## 5. 已排除或已有明确证据的点

### 不是简单的 RNG 偏差

两个场景的随机分支、候选选择和最终 RNG 都已对齐。不能通过“换种子”解释队列差异。

### 此前误判：不是导入器丢失原始高位（现已推翻）

导入器已逐项读取原始队列：

```text
toolId = raw & 0x7fff
discovered = (raw & 0x8000) != 0
```

当时顺序、重复项和原始高位校验均通过，190 许昌被记录为 `[tool-000, tool-016, tool-000]`。现已确认这些检查与导出共用错误的字节读取源，不能证明 U16 队列正确；许昌实际为 `[tool-007, tool-008, tool-012]`。

### 不是尚未进入道具分支

随机结果明确进入特殊搜寻的道具路径，不是无收获、人物、金钱或粮食路径。

### 不是当前 C# 实现造成的差异

差异是在 main 自己的生产 WASM 上观察到的，不是 Godot/C# 重写后才出现。

### 不是简单的“同源文件不同”

此前已确认 `3f0e168` 的同源 C 所用 `baye.js`、WASM 和 `SGBY.lib` 与 main 对应文件一致。因而需要继续查调用和运行时状态，而不是先假定版本不同。

## 6. 当前 Godot/C# 的处理

`MainSearchRules.ExecuteToolSearch` 当前：

- 使用 `ToolEntries.Where(entry => !entry.Discovered)` 构造候选。
- 按 main 顺序消耗 RNG 并选择道具。
- 校验道具条件。
- 生成发现道具报告。
- **没有将 `Discovered` 写成 true。**

这样处理是为了保留生产 WASM 已观察到的行为，而不是把同源 C 的 `0x8000` 预期冒充为生产 golden。

风险是：如果后续仍没有发现位结论，同一个队列项可能被再次搜寻。当前没有宣称防重复发现已经完成。

## 7. 待验证的可能原因

以下都只是假设，不是结论：

1. **调用条件未满足**：实际生产数据中的 `bole` 或执行者条件导致 `SetGoods` 没有执行到预期分支。
2. **队列读来源不同**：golden 读取的队列与 `SetGoods` 实际修改的队列不是同一视图或同一地址。
3. **运行时实现差异**：生产 WASM 中 `SetGoods` 的实际行为与同源 C 文本存在未被文件哈希直接揭示的调用路径差异。
4. **状态保存位置不同**：发现状态可能写入其他结构，而当前只检查了 `g_GoodsQueue`。
5. **观察时机问题**：队列可能在报告或后续阶段被重新加载，覆盖了写入结果。

必须通过运行时数据逐项排除，不能任选一种直接修改公式。

## 8. 建议的下一步实验

按以下顺序定位，通常前两项就能缩小范围：

1. **给 SetGoods 入口和循环插桩**  
   记录 `city、goods、ToolQueue、Tools、i、qc` 是否进入函数以及循环是否执行。

2. **同时记录写入地址和值**  
   每次循环输出 `g_GoodsQueue[i]` 的地址、修改前数值、修改后数值，再与 golden 读取地址比较。

3. **核对调用条件**  
   在 `SetGoods` 前记录 `fo`、`person`、`Order->City`、`p`，确认 `!fo || fo-1==person` 是否确实成立。

4. **直接调用 SetGoods 做最小实验**  
   不经 UI 和 SearchDrv，直接设置一个未知道具并调用，观察队列是否变化，以区分“函数无效”和“调用路径未到达”。

5. **检查报告后与存档中的状态**  
   比较接受时、PolicyExec 后、ConditionUpdate 后和保存文件中的队列，排除后续重载覆盖。

6. **必要时对照 SetGoodsByIndex**  
   只用于理解生产实现，不先把它当作替代修复方案。

## 9. 需要作出的行为决策

定位后需要明确：

- 如果生产函数实际没有写入，是否应按生产现状保留，还是按同源 C 修复为设置发现位。
- 如果写入被覆盖，是否应在正确阶段恢复发现位。
- 如果数据源或调用条件不同，应修改导入映射还是调用逻辑。

在结论出来前，**不建议直接写 `entry.Discovered = true` 来让测试变绿**。那只是选择了同源 C 的预期，尚未解释生产差异。

## 11. 2026-10-26 定位结论

在原始生产 WASM 上执行真实 `PolicyExec` 流程，并到达 `tacticStage4`，确认命令槽清空、人物归队。两个场景的原始 U16 队列分别为 `[0] → [32768]`、`[31] → [32799]`，最终 RNG 与原记录一致，月度更新后发现位仍存在。玩家/非玩家对照、开启/关闭只读断点共六个样本全部通过。

**根因是读取宽度错误：** 生产 `g_GoodsQueue` 反射元数据是 `ValueTypeU8=0`、元素宽度 1、长度 2000，但生产搜寻和 `SetGoods` 使用两字节寻址、`load16/store16`。`bridgeQueue[index]` 取的是字节，正确的队列项应从 `base + index * 2` 按 U16LE 读取。

北平写入后的原始字节是 `[31, 128]`，正确值为 `31 | 0x8000 = 32799`；旧读法只读到字节 `31`。原始 WASM 断点在 `0x48dc/0x48df` 确认同一地址的写入前后值。不是 `SetGoods` 漏写，不是伯乐限制，也不是写后被月度覆盖。报告确实发生在写入前，但无法解释写入后仍被误读的现象。

同一个读法还影响 `tools/main-import/import.mjs`，四时期分别有 13、17、13、17 条城市记录的导入道具队列与真实 U16 不符，共 60/152 条。`g_PersonsQueue` 的反射元数据为 U16、宽度 2，此次未发现相同的宽度问题。

复现工具为 `tools/main-import/diagnose-setgoods.mjs`，完整证据为 `docs/evidence/setgoods-diagnosis.json`。本轮仅完成定位和影响审计，没有修正导入内容、C# 发现位或原有 golden；这些修复及存读档/UI 回归仍须执行，不能据此宣称防重复搜寻已完成。
