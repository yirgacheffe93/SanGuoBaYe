# 33 · 架构边界改进实施计划

> 状态：阶段一至五已完成，阶段六待实施。依据 `32-architecture-review.md` 制定，审查基线为 `rewrite@47f4790`，当时 221 项测试全部通过。
>
> 实施原则：每次只推进一个阶段，先补能复现缺陷的测试，再修改实现；阶段验证通过后暂停汇报，再进入下一阶段。

## 1. 目标与顺序

本计划按“先修数据完整性，再修流程恢复，最后做结构拆分”推进：

1. 命令授权与人物位置一致性。
2. 命令输入和查询输出的集合所有权。
3. 历史存档的原始校验和与迁移边界。
4. 可恢复、可持久化的月度流程。
5. Godot 正常运行路径的应用层边界。
6. 战斗与命令职责的渐进拆分。
7. 内容、建局、运行状态与持久化合同的所有权。
8. 验证 fixture、R0 与工具公共设施的隔离。

A1–A4 是已复现的边界缺陷，优先处理；A5–A9 是结构演进，不与缺陷修复合并为一次大重构。

A1 放在 A2 后面，是因为可恢复月度阶段需要随存档保存。先建立正确的原始校验和与迁移顺序，再增加阶段字段，避免反复修改同一套加载逻辑。

A3、A4 放在最前面，是因为修改范围相对独立，可以先建立两条基础约束：非法输入零副作用，跨边界不共享可变对象。

## 2. 全局约束

- 不顺带调整玩法数值或扩充玩法范围。
- 不改变无缺陷路径的 RNG 调用顺序。
- 不为了通过测试而更新 golden；行为变化必须先确认属于目标缺陷。
- 保留 main 自动战斗的独立概率规则，不在结构重构中替换为手动战斗模拟。
- 不引入大型 DI 框架、通用消息总线或反射插件系统。
- 不为了形式上的不可变而强制引入新集合库，优先明确对象所有权并切断别名。
- 每个阶段独立验收，避免同时修改规则行为和大范围文件结构。
- 保留现有四个生产工程，优先在工程内部按业务模块组织；模块通过可见性和明确合同约束依赖，不以新增工程数或文件数作为完成标准。
- 原有 221 项测试是行为基线，不是架构验收的替代品。新增缺陷测试必须先在基线上失败，结构边界还须由独立的架构检查验证。
- 所有阶段均为待实施；本计划中的类型名和新增检查入口是实施目标，不表示已经存在或已经执行通过。

### 最终职责与依赖合同

| 模块 | 唯一职责 | 不应承担的职责 |
|---|---|---|
| Godot Composition | 创建具体依赖、连接应用合同和界面 | 规则计算、命令执行、存档迁移 |
| Godot Views | 展示快照、维护控件状态、发出操作意图 | 访问可变 World/Content、调用底层规则、读写文件 |
| Presenters / Navigation | 输入转换、刷新、错误展示及屏幕切换 | 战术计算、人物/资源写入、直接使用文件存储实现 |
| 应用命令与查询合同 | 定义用户操作、合法阶段、查询及结构化结果 | 向 UI 暴露可变状态或具体基础设施类型 |
| TurnCoordinator | 月度阶段、暂停与恢复、战局结束后的停止条件 | 内政数值、战术 AI 评分、存档字节格式 |
| BattleRules / Navigation | 战术行动、状态、公式、射程与可达性 | 战略城池、太守、势力胜负及文件存储 |
| TacticalAi | 选择动作并通过统一规则入口执行 | 复制伤害公式、另写移动限制、直接修改战略账本 |
| BattleOutcomeApplier | 一次性应用战果，协调人物、城市与势力更新 | 战斗内寻路、技能评分和 UI 展示 |
| 命令 Handler / 人员状态操作 | 命令自身规则及一致的人物迁移 | 绕过授权与阶段校验、维护相互冲突的位置账本 |
| NewGameFactory / Content | 不可变定义与显式建局 | 用运行时序列化规则隐式决定初值复制 |
| Persistence / Migrations | 按版本验证、迁移、存储与恢复快照 | 决定玩法流程、格式化 UI 文案 |

类名和拆分数量允许调整，但上述职责必须能独立定位、测试和约束。战略流程可以创建战斗并应用战果，战术规则不能反向依赖战略战果应用模块。战术规则需要的人物与兵力数据通过受限上下文提供，不继续向所有模块传递可任意写入的完整 World。

应用层定义存储、恢复及所需内容访问端口，Infrastructure 实现端口，具体实现只在组合入口连接。端口名称可按实际需求确定，不为单次纯计算额外创建接口。

共享的不可变 ID、值对象和枚举可以作为应用合同的一部分，架构守卫重点限制可变状态、具体实现和非法调用方向，不因命名空间前缀而禁止无害的值类型复用。

## 3. 阶段一：命令授权与位置一致性（A3）

### 修改范围

- 处斩、流放与其他命令一样，验证操作城市归属、目标当前城市和城市人物队列位置。
- 保留处斩、流放已有的目标状态差异，不顺便改变玩法规则。
- 将 `MainCommandService.IssueInternal` 收为非公开执行入口，正常命令只能通过校验后的入口进入。
- 仅抽取必要的人员离队、入城操作，保证城市队列、`CityId`、`OrderId` 等引用同步更新。
- 明确请求中的操作方、执行者与处置目标，不能用 UI 当前选中人物代替授权上下文。非法人物状态和忙碌目标在任何写入前拒绝。
- 定义人物位置不变量，区分在城、订单占用、战场和合法无位置状态；不把尚未出场或已处斩人物强行归入某座城市。

### 回归测试

- 跨城处斩和跨城流放被拒绝。
- 非操作方城市、原城队列不包含目标等非法请求被拒绝。
- 非法请求不改变状态 Hash，不消耗 RNG，不产生订单或部分扣费。
- 合法处斩、流放保持现有效果。
- 每名人物不会同时出现在两座城市的队列中。
- 城市、订单、战场间的位置引用和占用状态保持一致；测试覆盖非法处置忙碌人物及合法的无位置状态。

### 完成门禁

现有测试与新增测试全部通过；合法命令的既有 golden 不变。

## 4. 阶段二：输入与快照隔离（A4）

### 修改范围

- `MainExpeditionRules.Accept` 在接受命令时复制并校验 `ParticipantIds`，订单只持有自己的集合。
- `MainViewFactory` 不直接暴露 `MainCity.Connections` 等世界集合。
- `MainBattleViewFactory` 不直接暴露地图地形、地形类型或战斗日志集合。
- 查询结果与世界、内容保持独立；不能只把属性类型改成 `IReadOnlyList` 而继续共享底层 `List`。
- 检查嵌套对象与集合的所有权；普通查询合同不能返回可变 World、Content、领域实体或可用于修改其内部状态的对象引用。快照可以使用独立副本或真正不可变对象，不要求特定集合库。

### 回归测试

- 出征接受后清空或修改原请求列表，订单编队与人物占用保持一致。
- 修改城市视图中的连接集合，不影响真实 World。
- 修改战斗视图中的地形或日志，不影响 Content 或 ActiveBattle。
- 持有旧视图并推进会话，不会反向污染另一侧对象。
- 同一份静态内容创建两局游戏，一局的命令、查询或状态修改不影响另一局及剧本初值。

### 完成门禁

现有测试与新增所有权测试全部通过；正常 UI 显示和战斗查询行为不变。

## 5. 阶段三：历史存档校验与迁移（A2）

### 修改范围

- 先读取 envelope 和原始 `World` JSON，确定格式版本、重复键、必要字段及可支持范围；未知版本明确拒绝。
- 按对应历史 writer 的序列化合同验证 checksum，明确字段集合、顺序、命名、编码、转义和默认值行为。当前文件是格式化 JSON，checksum 来自紧凑序列化；不能直接哈希原始文本，也不能用最新 `MainWorld` 补齐字段后重算。
- 校验通过后按版本读取数据，检查历史结构的必要约束，执行迁移，再验证当前运行时的不变量。历史版本本来没有的字段由迁移补充，不能提前按当前模型的必填规则拒绝。
- ContentHash 兼容政策保持独立，不因为修复 schema 问题而放开不匹配内容。
- 本阶段先修复加载顺序和回归证据，不强制一次完成全部版本化 Save DTO。
- 为阶段七留下明确的版本 reader / checksum / migrator 接缝；临时方案同样必须遵守版本合同，不能引入另一套独立的加载路径。

### 回归测试

- 添加真实缺少历史字段的原生 schema 4/5 fixture。
- fixture 优先由对应历史 writer 生成并记录来源版本；保存原始校验和，不在测试中用当前实现重新生成期望值。
- 使用旧结构自身计算的校验和可以成功加载并迁移到当前 schema。
- 修改旧结构内容而不更新校验和，仍必须判定为损坏。
- 缺失字段、非法引用、内容 Hash 不匹配分别得到明确拒绝。
- 当前 schema 的保存、加载和回写保持兼容。
- 保留实施前 schema 6 writer 生成的文件，覆盖中文、转义字符、文件缩进，以及旧结构缺少后续字段的情况；校验的是对应版本的逻辑序列化合同，而非文件排版。
- envelope 与 World 的版本、内容标识必须一致；重复键、未知版本及篡改文件得到明确拒绝，加载失败不替换当前会话。

### 完成门禁

历史 fixture、损坏检测和当前存档回归全部通过；不再使用最新 `MainWorld` 补字段后重算校验和来冒充旧格式测试。

### 阶段三实施记录

## 6. 阶段四：可恢复月度流程（A1）

### 修改范围

- 在应用层建立 `TurnCoordinator`，由 `MainGameSession.EndMonth` 委托其推进流程。
- 明确玩家、AI、订单、等待战斗、月度更新等阶段及合法迁移。
- 定义并持久化最小恢复上下文：当前月份/阶段、已完成操作的识别方式、待处理订单及战斗的关联、战斗结束后的返回阶段。是否使用游标由实现决定，但不能仅保存阶段枚举就宣称可恢复。
- AI 完成后进入订单阶段；守城战斗结束后恢复订单阶段，不重新运行 AI。
- 区分玩家阶段主动出征与月末被动守城：前者回到合法的玩家操作阶段，后者回到被中断的月末处理位置。不得把所有战斗都固定恢复成玩家阶段或订单阶段。
- 支持同一月多场守城战，每场结束后继续正确位置。
- 明确订单执行顺序和完成标记，恢复时保持既有稳定顺序，不重复已完成订单，不遗漏尚未执行的命令。
- 每次关键状态迁移及战果应用后检查战局是否结束；结束后不再运行剩余 AI、订单、月度收入或粮耗。
- 命令入口验证操作阶段：暂停结算期间拒绝新增玩家战略命令，战斗输入仅在对应战斗阶段有效；重复提交结算或恢复操作不重复产生效果。
- 将月度阶段纳入快照和存档，并增加相应的当前 schema。
- 明确旧 schema 没有阶段字段时的迁移规则；无法从历史状态可靠推断的场景必须记录兼容边界，不能宣称完全恢复。
- 在迁移说明中列出旧档场景、可确定的恢复点及不确定场景的明确处理结果。无法可靠推断时返回可识别的不兼容错误并保留原文件，不静默猜测阶段或重跑 AI。
- 逐步限制 `ExecuteOrders`、`ConditionUpdate`、`EnterBattle` 等可绕过协调器的公开入口，同时保留测试所需的可控接缝。

### 回归测试

- 默认 `EndMonth()` 进入守城并结算后，AI 不重复执行。
- AI 补粮、内政增益、订单生成、收入及粮耗各只执行一次。
- 同一月多场守城战能依次恢复，不跳过剩余订单或月度更新。
- AI 后、战斗中、战斗后及订单恢复点的存读档与连续运行一致。
- RNG 状态和最终状态 Hash 与连续运行一致。
- 玩家主动出征返回、月末守城恢复、混合普通订单与多场战斗均有独立测试。
- 非法阶段发令、重复结算、重复恢复均不改变状态或 RNG；最终胜利/失败后不再执行剩余月度步骤。
- 只在协调器允许的安全边界保存；若支持 AI 后或订单间暂停，则提供可测试的安全暂停点，不要求在同步函数的任意语句处保存。

### 完成门禁

新增恢复测试、现有月度测试、长局测试和生产 golden 全部通过。恢复状态及 schema 迁移合同有文档记录，正常入口不再允许绕过协调器推进局面。

### 阶段四实施记录
