# 02 · 架构设计（草案）

> 目标：定义规则与界面分离的骨架。R0-S1 已验证 Godot + C#、独立 .NET 规则库，最终选型见 ADR-0008。回合细则见 `07-turn-rules.md`，UI 见 `08-ui-design.md`。

## 1. 架构目标

- 规则可无头运行：不启动 UI 也能跑完一局。
- 内容可数据化：新增城池/武将/事件不需要改代码。
- 回合可复现：同规则/内容版本、初始状态、随机算法版本与种子、命令序列 = 相同结果。
- UI 可替换：Godot 只是第一个表现层，不是规则的一部分。
- 可测试：每个系统都有单元/场景/回归测试。
- 可扩展：后续加战术战斗、mod、多剧本，不推翻核心。

## 2. 分层

```text
┌──────────────────────────────────────────────┐
│ Presentation（Godot UI / 输入 / 动画 / 音频）  │
│  - 只读 ViewModel，只发 Command               │
└───────────────▲──────────────────────────────┘
                │ ViewModel / Events
┌───────────────┴──────────────────────────────┐
│ Application（回合流程 / 命令调度 / 存档）       │
│  - TurnPipeline, CommandBus, SaveService      │
└───────────────▲──────────────────────────────┘
                │ Commands / Events
┌───────────────┴──────────────────────────────┐
│ Domain（规则 / 状态 / 计算 / AI 接口）          │
│  - World, Faction, City, Character, Army      │
│  - Economy, Personnel, Diplomacy, Battle, AI  │
│  - 纯逻辑，无引擎依赖                          │
└───────────────▲──────────────────────────────┘
                │ Data
┌───────────────┴──────────────────────────────┐
│ Content（JSON/CSV/本地化/校验器/编辑器）        │
└──────────────────────────────────────────────┘
```

代码依赖：Presentation → Application → Domain；内容加载/存储适配器实现 Application 定义的接口，将外部数据转换为领域定义。Content 文件是输入数据，不是 Domain 必须依赖的运行时模块。

当前工程划分：`Game.Domain`（纯 .NET）、`Game.Application`（纯 .NET）、`Game.Infrastructure`（JSON/文件存储）、`Game.Godot`（UI/适配）、`Game.Tests`。前三者不引用 Godot 类型；UI 通过应用层查询只读 ViewModel，不访问可变 World。R0-S1 已按此边界实现并验证。

## 3. 领域模型

| 实体 | 职责 | 关键字段（草案） |
|---|---|---|
| `World` | 一局游戏的根状态 | 剧本、年份/月份、回合、势力、城池、人物、军队、外交、事件队列、RNG |
| `Calendar` | 时间/季节 | 年、月、季节、天气 |
| `Map` | 地理拓扑 | 城池节点、道路、地形、关隘、水域 |
| `City` | 城市状态 | 归属、人口、农业、商业、城防、治安、粮草、金钱、守军、建筑、在城人物 |
| `Character` | 武将 | 姓名、字号、势力、位置、统率/武力/智力/政治/魅力、特性、技能、忠诚、体力、年龄、装备 |
| `Army` | 野外/出征部队 | 主将、副将、兵种、兵力、士气、补给、位置、行动力、状态 |
| `Unit` | 兵种模板 | 类型、攻防、机动、克制、地形修正、维护费 |
| `Item` | 装备/宝物 | 类型、属性修正、特技、稀有度 |
| `Faction` | 势力 | 君主、首都、金/粮只读汇总、声望、政策、外交关系、目标 |
| `Relation` | 双边关系 | 好感、停战/同盟、联姻、人质、条约期限 |
| `Event` | 事件定义/实例 | 触发条件、选项、效果、文本 key、一次性/可重复 |
| `Command` | 玩家/AI 指令 | 类型、发起者、目标、参数、校验结果、耗时 |
| `Order` | 已下达、待执行的命令 | 执行者、目标、剩余回合、前置条件、失败原因 |
| `Battle` | 战斗状态 | 攻守双方、战场、参战部队、回合、士气、天气、结果 |

### ID 与引用

- 所有内容使用稳定字符串 ID（如 `char.cao_cao`、`city.xuchang`），不用数组下标。
- 运行时不直接持有对象引用，跨模块用 ID + `World` 查询，便于存档和测试。
- 数值类型明确：资源/兵力使用整数，概率使用整数阈值，倍率采用整数比例并明确舍入；UI 可使用浮点绘图，规则计算不依赖 UI 浮点数。
- 静态定义与运行时状态分离：人物定义/剧本初值/人物当前状态分别保存；城市与势力资源各有唯一账本，原型仅城市持有金粮，势力总量是只读汇总。

## 4. 回合流程

```text
TurnStart
  ├─ 进入指定回合；按回合计算日期，原型每回合一月
  ├─ 收入 → 唯一一次维护/补给结算 → 缺粮影响
  ├─ 到期条约处理、回合开始事件
  └─ 玩家可见状态更新

PlayerPhase
  ├─ 校验指令、原子扣费/占用执行者、创建 Order
  ├─ 查看预计效果、任务队列；取消尚未开始的本回合任务
  └─ 结束回合

AIPhase
  ├─ 所有 AI 根据同一阶段起点的只读快照规划
  └─ 按 faction_id 提交，复用玩家的校验/扣费/任务接口

Resolution
  ├─ 本回合新增任务标记为执行中，所有任务推进一次
  ├─ 到期开发/征兵 → 到期运输 → 外交 → 行军到达
  ├─ 按目标城市分组，自动战斗 → 伤亡/归属应用
  └─ 前置条件失效的任务失败；释放占用、生成原因

TurnEnd
  ├─ 回合末事件（原型仅报告型事件）
  ├─ 胜负/结局检查
  └─ 回合报告、完整快照；未结束则进入下一回合
```

关键原则：

- **命令不是立即生效**：大部分命令会进入 `Order` 队列，按耗时/距离在后续回合结算；这让“等待”和“补给”有意义。
- **执行顺序稳定**：按上面的阶段执行；阶段内按任务类别优先级、目标 ID、创建回合、势力 ID、命令序号排序。具体冲突规则见 `07-turn-rules.md`；稳定排序不等于公平，试玩需要观察先后手优势。
- **失败有原因**：命令校验失败返回结构化原因，UI 直接展示，不靠猜。

## 5. 命令 / 事件模型

```text
Command -> Validator -> Accepted / Rejected(reason)
Accepted -> Domain handler -> 更新 World + 返回 Events -> 查询新 ViewModel
```

- 每个命令类型有：参数 schema、校验函数、执行函数、耗时/成本、日志格式。
- 规则处理器是可变 World 的唯一写入者；事件是执行后的通知和战报，不承担重建全部状态的职责。首版采用快照存档，不实现完整事件溯源。
- 一个命令的校验、扣费、执行者占用与任务创建必须原子完成；失败不留下部分修改。查询预计结果不修改状态，也不消耗随机数。
- 事件可序列化，用于回放、调试、战斗日志、成就统计（后续）。
- 命令和事件都带 `turn` / `seq`，便于排序和重放。

## 6. 战斗

分两层，避免 MVP 被战术棋盘拖死：

### 6.1 战略层（MVP）

- 遭遇战/攻城触发 → 生成 `BattleSetup`（双方部队、地形、士气、补给、天气）。
- `BattleResolver` 按回合模拟：远程、接战、伤亡、士气、溃败、追击。
- 输出结构化战报：每回合伤害、技能、士气变化、结果。
- UI 先做战报面板，不做战场动画。

### 6.2 战术层（v1）

- 六边形或方格战场；单位、地形、朝向、士气、计谋、天气。
- 与战略层共用 `Unit`/`Army` 数据，但战斗状态独立。
- 战斗 AI 与战略 AI 分离；战术 AI 可以用效用评分。
- 可切换“自动结算/亲自指挥”，自动结算必须和手动结果使用同一套底层公式。

### 6.3 接口

```text
BattleResolver.resolve(setup, rng) -> BattleResult
TacticalBattle.start(setup) -> BattleState
TacticalBattle.issue(command) -> events
TacticalBattle.finish() -> BattleResult
```

## 7. AI

分三层，独立于 UI：

1. **战略 AI**：势力目标（生存/扩张/经济/外交），评估战争收益、结盟、发展优先级。
2. **运营 AI**：军队集结、目标城市选择、补给线、防守重点。
3. **战术 AI**：战斗内移动/攻击/技能（v1）。

要求：

- 确定性：相同状态 + 种子 → 相同决策。
- 可解释：记录评分/原因，便于调试。
- 难度分级：通过信息量、反应速度、资源加成区分，不靠作弊式随机。
- 可降级：MVP 可以先用规则式 AI（if/else + 评分），不追求机器学习。

## 8. 内容与数据

- 格式：JSON（结构化数据）+ CSV/表格（数值/文案批量编辑）+ 本地化 key。
- 每类内容有 schema（JSON Schema 或自定义校验器），构建时校验：
  - 必填字段、类型、范围
  - 悬空 ID（人物/城市/事件/道具）
  - 重复 ID、循环引用
  - 本地化缺失
- 内容包：`content/base/`、`content/scenarios/`、`content/locale/`。
- 运行时只读内容包；mod 以后用同样的包格式。
- 数值表与规则代码分离：公式在代码，参数在数据。

## 9. 表现层（Godot）

- 场景：主菜单、剧本选择、世界地图、城池、人物、外交、战斗、事件、存档、设置。
- 每个场景只做三件事：读 ViewModel、发 Command、播动画/音效。
- 输入：鼠标优先，键盘快捷键；不做方向键焦点导航。
- UI 状态（选中、筛选、排序）属于表现层，不写入 `World`。
- 地图渲染：城池/道路/势力边界/部队图标分层；后续可换 TileMap 或自绘。
- 文本：中文字体、标点、换行、长文本滚动；本地化从第一天就用 key。

## 10. 存档

- 快照式：`schema_version`、`game_version`、`rules_version`、`content_version/hash`、`rng_algorithm_version`、`seed`、RNG 当前状态、`turn/phase`、序号计数器、待执行任务、`World` 全量状态。
- 原型只在 PlayerPhase（AI 尚未规划）或 TurnEnd 安全点存档；载入时明确下一阶段，不能重复发收入或扣维护费。
- 迁移：版本 N → N+1 的迁移函数；不兼容时明确提示。
- 校验：CRC/哈希加结构/引用/资源不变量校验；先写临时文件，校验成功后原子替换，保留上一份好档。校验和只用于检测损坏。
- 自动存档 + 手动槽位；后续 Steam Cloud 只需换存储后端。
- 回归回放必须支持同版本的初始快照/种子 + 玩家命令日志（含结束回合、取消和事件选择）；AI 决策可再生成，另存诊断日志。玩家观看回放的 UI 后置。
- 所有规则遍历显式排序；AI 同分按稳定 ID 决胜；固定随机算法及版本，UI/音效使用独立随机源。核心状态哈希使用规范化序列化，排除时间戳、UI 状态等非规则字段。

## 11. 测试

| 层级 | 内容 |
|---|---|
| 单元测试 | 公式、校验、资源结算、战斗伤害、AI 评分 |
| 场景测试 | 固定剧本 + 固定命令序列 → 断言状态 |
| 回归/黄金 | 种子 + 命令 → 状态哈希；改规则必须显式更新 |
| 连续性与不变量 | 连续游玩与中途读档结果相同；资源非负；武将不重复占用；兵力无复制 |
| 内容校验 | 所有内容包通过 schema/引用检查 |
| UI 冒烟 | 启动 → 新游戏 → 存读档 → 退出 |

要求：优先 C# 方案下，Domain/Application 的规则测试可用 `dotnet test` 在未安装 Godot 的环境运行；Godot UI 冒烟测试单独运行。GDScript 备选只承诺 Godot headless，不能视为满足同一条验收。

## 12. 本地化 / Mod（后置）

- 文本全部 key 化；中文先行，英文后补。
- 数据 mod：同一套内容包格式，加载顺序和覆盖规则明确。
- 脚本 mod：v1 不做；以后评估沙箱方案（Lua/WASM），不要直接执行任意代码。

## 13. 性能目标

- 一回合结算（含 AI）< 200ms（MVP 规模）。
- UI 60fps；地图滚动/缩放不卡顿。
- 存档 < 1s；内存 < 1GB。
- 大规模战斗（v1）单独压测。

## 14. 开放问题

1. 技术栈：Godot + GDScript vs Godot + C#（见 `04-tech-selection.md`）。
2. 原型/MVP 固定采用城池图 + 道路；战术层另做评估。
3. 原型/MVP 固定采用自动战斗 + 战报；战术层不进入 G1/G2。
4. 人物属性：五维（统武智政魅）还是更细的分项？
5. 原型每回合一月，所有耗时用整数回合；是否调整由试玩决定。
6. 先验收 3–5 城/8–12 人原型，再评估扩至 MVP 20 城/60 人。
7. 美术风格：写实、国风插画、像素？影响 UI 和成本。
8. 剧本叙事：历史事件驱动，还是势力自由发展为主？

这些问题的答案应写成 ADR，而不是停留在讨论里。
