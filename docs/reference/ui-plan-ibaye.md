# 《三国霸业》Godot 4 UI 视觉改造规划

## 1. 项目定位

基于 [baye-alpha](https://github.com/kvinwang/baye-alpha) 和 [iBaye](https://gitee.com/bgwp/iBaye)，保留《三国霸业》的三国历史背景、武将、剧情、规则和策略玩法，以 Godot 4 重构 UI 与点按交互，先推出 macOS 版本，后续适配 Windows 与 Steam Deck。

**视觉关键词：写实、历史战争、英雄气质、克制的史诗感。** 不使用二次元人物设计、像素风或夸张卡通造型；不追求昂贵的全 3D 战场。

## 2. 视觉参考

| 游戏 | 重点借鉴 | 避免照搬 |
|---|---|---|
| [《全面战争：三国》](https://store.steampowered.com/app/779340/Total_War_THREE_KINGDOMS/) | 写实英雄肖像、史诗氛围、暗色金属 UI、历史质感 | 大规模 3D 战场与复杂系统 |
| [《三国志14》](https://store.steampowered.com/app/872410/ROMANCE_OF_THE_THREE_KINGDOMS_XIV/) | 武将立绘、地图标记、人物属性信息组织 | 过密的表格和复杂操作层级 |
| [《汉末霸业》](https://store.steampowered.com/app/577230/Three_Kingdoms_The_Last_Warlord/) | 轻量策略的城池经营与菜单结构 | 过度拟古和繁杂装饰 |

> 建议的定位：**《全面战争：三国》的英雄气质 + 《三国志14》的写实人物 + 《汉末霸业》的轻量策略交互。** 以上为设计参考，不直接复用其他游戏受版权保护的美术素材。

## 3. 核心画面设计

### 3.1 战略地图

- 采用 **2D 手绘写实地图 / 轻量 2.5D 视觉**：山脉、河流、平原与城池体现真实地理层次。
- 保留原版地图和行动规则，弱化棋盘线条，但选中和移动范围必须清楚。
- 城池使用写实古建筑图标，军队使用旗帜、兵种标识或武将肖像。
- 点击城池或武将直接显示信息面板；可拖动浏览地图。
- 美术先做一小块地图样板，再评估全地图重绘成本。

### 3.2 武将界面

- 使用 **半身写实历史插画**，突出盔甲、武器、披风、人物神态。
- 著名武将优先设计专属肖像；普通人物采用统一、可扩展的视觉规范。
- 属性、状态和可执行操作采用现代卡片式排版，文字优先确保易读。
- 英雄感主要来自立绘、构图与适度的微动效，而不是复杂 3D 动画。

### 3.3 城池与内政面板

- 点击城池后展开侧边栏，展示归属、资源、驻军、武将等信息。
- 常用动作直接呈现，深度操作放进「更多」或统一菜单。
- 大量数据使用分组、标签和明确的层次，不让仿古纹理影响阅读。

### 3.4 战斗界面

- 保留回合制战斗及数值规则。
- 点击己方单位 → 显示合法行动 → 点击目的地或目标 → 执行操作。
- 使用地块高亮、范围边界、目标提示和简短反馈动画，不依赖传统方向键光标。

### 3.5 主菜单与系统界面

- 背景可用写实战争场景插画、旌旗、山河或古战场剪影。
- 使用克制的暗金、深灰、朱红，避免过度堆叠龙纹、卷轴和拟物按钮。
- 菜单提供新游戏、继续游戏、读档、设置、退出等入口。

## 4. UI 规范

### 4.1 推荐配色

| 色彩 | 色值 | 用途 |
|---|---|---|
| 玄铁黑 | `#181C22` | 主背景、深色面板 |
| 青灰 | `#333C46` | 次级面板、分隔区域 |
| 古金 | `#B89A62` | 标题、重要边框、核心操作 |
| 朱红 | `#963D37` | 战斗、警示、重要选择 |
| 羊皮纸 | `#D9CEB5` | 浅色文本区、柔和背景 |

### 4.2 组件规范

- **字体：**正文使用清晰的现代中文字体；书法风格仅用于标题或章节名。
- **按钮：**大面积可点击、状态明确，悬停/按下/禁用反馈一致。
- **面板：**统一边距、字号、信息层级和圆角/边框规范。
- **图标：**线性或写实小图标保持同一套笔触和光照方向。
- **动效：**面板滑入、选中高亮、轻量粒子反馈即可；不牺牲操作速度。

## 5. 点按式交互架构

核心流程：**点击对象 → 展示信息 → 选择操作 → 点击目标 → 按原版规则执行**。

- 取消旧式「方向键选项 + 确认键」的 UI 交互。
- 地图对象直接选中，常用操作显示在上下文面板。
- 固定菜单按钮承载内政、军事、人事、存读档和系统设置等深度操作，菜单项以原游戏已有功能为准。
- Godot 的表现层通过 `Game API` 查询状态和提交指令，避免直接修改规则数据。
- 鼠标点按是第一版的主要交互；未来将触屏与手柄映射到统一的语义操作层。

## 6. Godot 4 实施方式

- **Godot 4：**负责地图渲染、Control UI、鼠标点击和窗口适配。
- **iBaye C 核心：**尽量保留内政、战斗、回合和剧情等原规则。
- **GDExtension / 适配层：**提供获取城池、查询武将、获取允许指令、执行操作、保存和读取等接口。
- **关键前提：**先审计 iBaye 的规则、绘制和旧输入逻辑耦合程度。若强耦合，迁移工作量可能明显增加。

### 最小技术验证

先实现一条真实闭环：**Godot 中点击成都 → 显示原版城池数据 → 点击一项原版内政指令 → iBaye 计算结果 → Godot 刷新数值**。

闭环验证通过后，再全面迁移界面，避免直接开始大规模重构。

## 7. 美术资源优先级

以下是**建议的美术制作工作量分配**，不是开发进度预测：

| 内容 | 比例 |
|---|---:|
| 武将写实立绘 | 40% |
| 战略地图与城池 | 30% |
| UI、菜单及图标 | 20% |
| 战斗特效和动效 | 10% |

建议先做 **一张主菜单、一张战略地图、一张武将详情面板** 的统一视觉样板，确认风格后再扩展美术生产。

## 8. 里程碑

- [ ] M1：审计 iBaye 输入/规则/渲染代码的耦合程度。
- [ ] M2：完成 Godot + 原规则的城池操作闭环。
- [ ] M3：确定写实三国 UI 视觉样板与组件规范。
- [ ] M4：完成战略地图、武将和城池界面的点按改造。
- [ ] M5：完成战斗、深度菜单、剧情与存读档 UI。
- [ ] M6：macOS 完整流程测试及可分发构建。
- [ ] M7：再推进 Windows、Steam Deck 与 Steam 接入。

## 9. 主要风险

1. **引擎耦合：**旧输入、绘制和规则可能难以拆开；先做接口验证，再决定迁移范围。
2. **美术成本：**写实武将与地图需要统一风格，优先使用小范围样板验证制作成本。
3. **交互复杂度：**传统深层菜单迁移为点按 UI 时，需要逐项梳理操作状态与规则约束。
4. **版权授权：**原游戏的代码、图像、音乐和具体剧情表达需要分别核实商业使用和再发行权利；参考游戏的美术不可直接复制。

## 10. 最终建议

**先做 macOS 上可运行的 Godot 4 样板，不急着移植全游戏。** 技术上先证明能复用原版游戏计算；视觉上先确认「写实英雄肖像 + 手绘战略地图 + 玄铁暗金 UI」的方向。之后逐步完成完整的鼠标点按交互，再扩展到其他平台。
