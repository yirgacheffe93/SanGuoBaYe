# 《三国霸业》Godot 4 现代化改造规划

> 注（2026-10-22）：这是最初的规划。P0 验证后部分假设已修正——iBaye 没有现成的规则 API，界面与规则耦合在阻塞式 C 循环里。当前实现见 `docs/architecture.md` 和 `docs/p0-report.md`，工程已移到仓库根目录。

## 1. 项目概述

### 1.1 项目背景

基于开源项目 [baye-alpha](https://github.com/kvinwang/baye-alpha) 及其底层 [iBaye](https://gitee.com/bgwp/iBaye) 游戏引擎，对经典游戏《三国霸业》进行现代化改造。

项目目标不是重新设计游戏，而是保留原有玩法，通过现代游戏引擎改善运行环境、操作体验和 UI 表现，最终实现 Steam 多平台发行。

### 1.2 核心原则

- **玩法不变**：保留原版三国背景、武将、剧情、数值和战斗机制。
- **交互重做**：淘汰方向键导航与确认操作，全面采用鼠标点按交互。
- **UI 重做**：使用现代化界面布局，提升画面质量和操作体验。
- **逻辑复用**：尽可能保留现有 C 语言游戏逻辑，避免从零重写。
- **渐进开发**：先实现 macOS 版本，再逐步支持 Windows 和 Steam Deck。
- **架构解耦**：游戏规则、UI、输入和平台功能相互独立。

## 2. 技术选型

| 模块 | 技术方案 | 说明 |
|---|---|---|
| 游戏引擎 | Godot 4 | 负责 UI、渲染、交互及平台支持 |
| 开发语言 | GDScript + C/C++ | GDScript 开发界面，C/C++ 复用旧逻辑 |
| 原有游戏核心 | iBaye | 尽可能复用游戏规则、数据与计算逻辑 |
| 原生接口 | GDExtension | 连接 Godot 与原有 C 代码 |
| 地图系统 | Godot TileMapLayer | 重新实现地图显示和点击交互 |
| UI 系统 | Godot Control | 武将、城池、菜单、战斗等界面 |
| 存档系统 | 本地存档适配层 | 尽量兼容原版存档，预留 Steam Cloud |
| 首发平台 | macOS | 优先支持 Apple Silicon |
| 后续平台 | Windows / Steam Deck | 复用核心代码并适配不同平台 |

**技术原则：不使用 Godot 重写整套游戏规则，而是优先将 Godot 作为新的表现层和交互层。**

是否能够直接复用原 iBaye 的核心逻辑，需要通过源码分析和技术验证确定。

## 3. 目标系统架构

```text
Godot 4
│
├── UI 表现层
│   ├── 主菜单
│   ├── 战略地图
│   ├── 武将信息
│   ├── 城池管理
│   ├── 战斗界面
│   └── 系统设置
│
├── 输入与交互层
│   ├── 鼠标点按
│   ├── 触控操作
│   ├── 地图对象选择
│   ├── 上下文操作菜单
│   └── 全局菜单
│
├── Game API
│   ├── 游戏状态查询
│   ├── 武将与城池查询
│   ├── 游戏指令执行
│   ├── 事件通知
│   └── 存档读写
│
└── iBaye Core（C 语言）
    ├── 游戏规则
    ├── 内政系统
    ├── 战斗计算
    ├── 武将与城池数据
    ├── 剧情与事件
    └── 存档逻辑
```

目标是让 Godot 负责界面及交互，iBaye 负责游戏状态和规则计算。

如果旧代码中的规则、渲染、按键状态机高度耦合，需要先拆分相关模块，再接入 Godot。

## 4. 核心改造范围

### 4.1 保留的部分

尽可能直接复用或在不改变行为的前提下迁移：

- 武将、城池、势力等基础数据
- 三国历史背景和剧情事件
- 内政与资源计算规则
- 武将属性、技能及装备机制
- 战斗伤害、移动范围等计算规则
- 回合推进与游戏胜负判定
- 存档数据及游戏状态

原有规则作为游戏行为基准，避免重构导致数值或玩法发生变化。

### 4.2 重构的部分

| 系统 | 改造内容 |
|---|---|
| 游戏渲染 | 使用 Godot 重新绘制地图、角色和界面 |
| 输入系统 | 移除传统方向键菜单交互，采用鼠标点按 |
| 主菜单 | 重做开始游戏、读档、设置等界面 |
| 地图交互 | 点击城池、武将、地图格子直接选择对象 |
| 战斗交互 | 点击部队、移动目标、攻击目标 |
| 信息面板 | 重新设计武将、城池、装备等信息布局 |
| 深度操作菜单 | 增加统一菜单按钮，组织复杂游戏操作 |
| 分辨率适配 | 支持不同窗口大小和屏幕比例 |

不额外增加新玩法、新系统和新剧情。

## 5. 新交互设计

### 5.1 基本操作原则

取消原版的方向键焦点导航和确认键交互，将操作方式统一为：

**点击对象 → 查看信息 → 选择操作 → 点击目标 → 执行指令**

主要包括三种交互：

1. **直接点击**：选择武将、城池、部队或地图格子。
2. **上下文操作**：根据当前选中对象显示可执行操作。
3. **全局菜单**：通过菜单按钮进入内政、军事、物品和系统功能。

### 5.2 地图交互

点击城池：

- 选中城池
- 显示城池信息
- 提供可用操作入口

点击武将：

- 显示武将属性和当前状态
- 提供移动、攻击、详情等合法操作

点击空白地图：

- 根据当前操作状态，选择目标格子或取消选择
- 支持地图浏览和拖动

### 5.3 深度操作菜单

在主游戏界面设置固定的菜单入口。

根据游戏原有功能组织菜单，例如：

```text
菜单
├── 内政
│   ├── 城池管理
│   ├── 资源管理
│   └── 人事管理
├── 军事
│   ├── 部队管理
│   └── 军事指令
├── 游戏
│   ├── 存档
│   ├── 读档
│   └── 游戏设置
└── 返回游戏
```

具体菜单项需要与原版实际功能对应，不引入原游戏不存在的额外规则。

### 5.4 输入架构

新 UI 不再依赖传统的方向键驱动。

通过统一的游戏操作接口执行指令，例如：

```text
select_general(general_id)
select_city(city_id)
move_unit(unit_id, target_position)
attack_target(unit_id, target_id)
execute_city_action(city_id, action_id)
```

以上为目标接口示例，并非原引擎已有 API。

所有操作仍需通过原游戏规则进行合法性校验，不能绕过回合、资源、距离等限制。

## 6. UI 视觉设计

### 6.1 设计方向

采用 **现代复古 2D 策略游戏风格**。

- 保留经典三国游戏氛围。
- 优化地图颜色、地形细节和角色表现。
- 使用统一的按钮、弹窗和信息面板。
- 提高文字清晰度与信息可读性。
- 使用适量动画增强点击与操作反馈。
- 保持界面简洁，避免复杂的视觉装饰。

### 6.2 改造优先级

1. 主菜单
2. 战略地图
3. 武将信息面板
4. 城池管理界面
5. 战斗界面
6. 其他系统菜单

UI 设计需预留 Steam Deck 的 1280×800 屏幕适配空间，但第一版只要求 macOS 桌面体验完整。

## 7. 分阶段开发计划

### P0：原引擎分析与技术验证

**目标：确定 Godot 迁移是否可行，避免盲目全面重构。**

工作内容：

- [ ] Fork baye-alpha 和 iBaye 项目。
- [ ] 梳理现有工程结构及构建方式。
- [ ] 分析游戏规则、输入和渲染模块的耦合关系。
- [ ] 找到游戏状态读取和执行指令的核心入口。
- [ ] 确认原有资源和存档格式。
- [ ] 调查 C 语言核心通过 GDExtension 接入 Godot 的可行性。

验收标准：

能够明确哪些模块可以复用、哪些必须重构，并形成接口清单。

### P1：Godot 最小可运行原型

**目标：验证新 UI 能否调用真实的原版游戏逻辑。**

工作内容：

- [ ] 创建 Godot 4 工程。
- [ ] 建立基础地图场景。
- [ ] 实现鼠标点击选中城池。
- [ ] 展示真实的原版城池信息。
- [ ] 实现一个真实的原版内政操作。
- [ ] 将执行结果同步到 Godot UI。

验收标准：

完成以下闭环：

```text
点击城池
  ↓
Godot 读取城池信息
  ↓
显示城池操作面板
  ↓
点击一项内政指令
  ↓
iBaye 执行原版计算
  ↓
Godot 刷新游戏状态
```

**这是项目最重要的技术里程碑。**

如果这一阶段发现规则与旧 UI 难以拆分，需要重新评估迁移成本，必要时保留原 H5 技术路线。

### P2：基础 UI 和地图系统

工作内容：

- [ ] 实现现代化主菜单。
- [ ] 重做战略地图渲染。
- [ ] 实现城池、武将和地图点击选择。
- [ ] 实现上下文操作面板。
- [ ] 实现统一菜单入口。
- [ ] 实现窗口尺寸自适应。

验收标准：

玩家可以不使用方向键，完成基础地图浏览、对象选择和城池操作。

### P3：完整游戏交互迁移

工作内容：

- [ ] 迁移武将相关操作。
- [ ] 迁移城池和内政操作。
- [ ] 迁移军事及部队操作。
- [ ] 重做战斗画面和点按交互。
- [ ] 接入回合推进、事件和剧情交互。
- [ ] 接入存档和读档功能。

验收标准：

玩家能够通过新的点按界面完成原版完整游戏流程，不需要旧式方向键操作。

### P4：macOS 版本完善

工作内容：

- [ ] 优化 UI 视觉效果。
- [ ] 优化窗口缩放和全屏体验。
- [ ] 验证 Apple Silicon 运行稳定性。
- [ ] 检查性能、资源加载与内存占用。
- [ ] 完成完整游戏流程测试。
- [ ] 制作 macOS 应用构建包。

验收标准：

macOS 平台可独立运行，原版主要玩法、剧情、战斗及存档功能完整可用。

### P5：跨平台与 Steam 发行

在 macOS 版本稳定后进行。

- [ ] 支持 Windows 构建与测试。
- [ ] 验证 Linux 或 Steam Deck Proton 运行方案。
- [ ] 增加触控及手柄操作适配。
- [ ] 适配 Steam Deck 小屏幕 UI。
- [ ] 评估 Steam Cloud 和成就系统。
- [ ] 完成 Steam 商店及发行准备。

## 9. 核心风险与应对

| 风险 | 应对方式 |
|---|---|
| 原游戏逻辑与输入高度耦合 | 优先提取规则接口，先验证一条完整操作链 |
| Godot 无法直接使用旧引擎 | 通过 C/C++ 适配层接入，不直接依赖旧 WebAssembly |
| 迁移导致原版玩法变化 | 建立原版行为对照及回归测试 |
| 存档不兼容 | 保留旧格式解析能力，必要时开发存档转换工具 |
| UI 重做工作量过大 | 优先通用组件和核心游戏场景 |
| 后续平台适配困难 | 隔离系统相关代码，避免使用 macOS 专属接口 |
| 原游戏版权授权不明确 | 商业发行前核实原代码、游戏内容和素材的授权范围 |

## 10. 第一版范围控制

第一版只实现：

- macOS 原生运行
- Godot 4 新 UI
- 鼠标直接点按操作
- 统一菜单及上下文操作面板
- 原版完整游戏流程
- 本地存档与读档

第一版不实现：

- 新剧情、新势力、新武将
- 新战斗机制
- 多人联机
- Steam 创意工坊
- Steam 成就和云存档
- Windows、Steam Deck 的正式适配

## 11. 最终实施建议

采用 **Godot 4 + 原 iBaye 游戏核心** 的渐进式重构方案。

整体重构边界：

- **保留**：游戏数据、数值规则、战斗算法、剧情事件。
- **重构**：游戏渲染、UI、输入系统、菜单状态机。
- **新增**：Game API、Godot 适配层、跨平台构建能力。

不要直接开始全面重写，也不要一次性迁移所有游戏模块。

**第一步只做一件事：在 Godot 中点击一座真实城池，执行一次原版内政操作，并正确更新游戏状态。**

只要完成这个技术闭环，就可以以此为基础逐步迁移地图、武将、战斗和全部 UI。

项目最终目标是：

**在完整保留《三国霸业》经典策略体验的基础上，打造一款现代化、全鼠标操作、可持续迭代，并具备 Steam 多平台发行能力的 2D 三国策略游戏。**
