# 06 · 架构决策记录（ADR）

> 一条决策一个编号。决策改变时不要改历史，新增一条“取代/修订”记录。

## ADR-0001：放弃 iBaye 作为生产代码

- 状态：已接受
- 日期：2026-10-23

### 背景

iBaye 是步步高 A600 引擎的跨平台 C 移植，包含《三国霸业》的规则、界面、平台层。我们已经验证它可以在 macOS 原生运行（见 `godot` 分支 P0），但它：

- 规则与 1bpp 界面、阻塞按键循环深度耦合；
- 代码风格古老，全局状态多，难以做现代 UI；
- 授权不清晰（MIT 代码 + 步步高版权头 + 未授权素材）；
- 无法满足“完全重构、全新内容”的目标。

### 决策

- 新工程**不包含、不链接、不复制** iBaye 的代码。
- iBaye 只保留为**高层行为参考**：用于理解回合节奏、系统边界，不作为实现来源。
- `godot` 分支保留 P0 验证代码，供对照/复盘；不合并进 `rewrite`。

### 后果

- 失去现成的规则、AI、战斗、存档兼容；需要重新实现。
- 需要先写规格和测试，不能靠“照抄代码”推进。
- 代码/架构自由度高，可按现代工程方式设计。
- 仍需遵守 clean-room 规则，避免复制原版表达。

### 备选

- 保留 iBaye 核心 + 控件桥接：技术上可行，但不符合“完全重构/全新内容”的目标。
- 继续用 iBaye + 换皮：授权与维护风险最高。

## ADR-0002：精神续作，而不是复刻

- 状态：已接受
- 日期：2026-10-23

### 背景

原游戏的代码、数据、美术、文本、音乐、名称授权不清晰；直接复刻在法律和创作上都不合适。

### 决策

- 使用公共领域的三国历史作为题材。
- 玩法借鉴类型惯例，但**具体表达全部原创**：代码、数值、地图、美术、文本、音乐、UI、名称。
- 不使用原版 `.lib`、截图、数据表、字体、Logo 作为新工程内容。
- 维护来源记录；发行前做商标/法律审查。

### 后果

- 内容工作量显著增加（人物、事件、地图、美术）。
- 法律风险降低；可以独立发行（仍需商标检索）。
- 产品定位是“受经典启发的新游戏”，不是“复刻版”。

### 备选

- 忠实复刻（沿用原版数据/美术）：工作量小，但授权风险高，不符合目标。
- 只换代码、保留内容：同样受内容授权约束。

## ADR-0003：技术栈（待定）

- 状态：提议中
- 日期：2026-10-23

### 背景

需要 2D UI、复杂规则/AI、数据驱动、无头测试、macOS/Windows 导出。候选：Godot + GDScript、Godot + C#、Unity + C#、自研。

### 当前倾向

- 引擎：Godot 4。
- 语言：C# 优先（规则/AI/测试），GDScript 作为备选（单人快速迭代）。
- 最终选择在 R0 的 1–2 周 spike 后确定。

### 需要补充

- spike 数据（代码量、测试速度、UI 绑定、构建/导出）。
- 开发者对 C#/.NET 的熟悉程度。
- 是否接受两语言混用（默认不建议）。

### 后果（待定）

- 若选 C#：构建链更重，但领域代码更稳。
- 若选 GDScript：迭代快，但需要更强的静态类型/模块纪律。

## ADR-0004：`rewrite` 使用 orphan 分支

- 状态：已接受
- 日期：2026-10-23

### 背景

旧仓库同时包含 H5/Electron 版本和 iBaye P0；新项目要完全重写，不应继承旧历史和旧文件。

### 决策

- 新建 orphan 分支 `rewrite`，只有一个初始提交，无父历史。
- `main` 保留旧 H5/Electron 版本。
- `godot` 保留 iBaye P0 参考。
- 三套代码互不合并；需要参考时用 `git show`/worktree。

### 后果

- 新分支 `git log` 干净；不会误用旧代码。
- 无法直接 cherry-pick 旧实现；这是有意的。
- 三个分支的文档/资产需要明确归属，避免混淆。

### 备选

- 在 `godot` 分支上继续改造：会保留旧历史和 iBaye 代码，不符合“从 0”。
- 新建独立仓库：更彻底，但参考实现/资料分散；暂不需要。

## ADR-0005：先验收小原型，规则与最小 UI 同步交付

- 状态：已接受
- 日期：2026-10-23
- 背景：原规划 R1 没有正式 UI，R2 同时承担首次试玩和 20 城/60 人内容生产；宪章 2–3 小时与 R2 30–60 分钟的口径不一致。
- 决策：R1 为 3–5 城、2 势力、8–12 武将的 15–30 分钟可玩原型，规则与最小 UI 同步；R2 才扩为 2–3 小时 MVP；道具/装备/编辑器/战术棋盘不进原型，MVP 也不要求道具或全部独立头像。
- 验证：G1 至少 3 名、G2 至少 5 名外部玩家试玩；阻塞问题修复复测，不能以文档或样片替代。
- 后果：需要较早投入 UI，但能先验证成本、任务和结果是否易懂；R3 以后是候选扩展，工期在 MVP 后重新估算。
- 备选：领域核心全部完成后再接 UI；不采用，交互问题反馈太晚。
- 复审条件：外部试玩表明原型仍过大或核心循环无趣时，先缩范围或改规则再扩内容。

## ADR-0006：快照存档与同版本确定性

- 状态：已接受
- 日期：2026-10-23
- 背景：“固定种子”不足以保证读档继续或跨版本复现；原架构对通知事件和事件溯源边界不明确。
- 决策：命令处理器修改 World 并返回通知事件；采用快照存档，不做完整事件溯源。保存规则/内容/随机算法版本、RNG 当前状态、阶段、序号和待执行任务；所有规则遍历和同分处理显式排序。
- 验证：同版本、同初始局面和命令重复运行一致；中途读档继续与连续游玩一致；UI 预览不改变核心随机状态。
- 后果：原型仅在 PlayerPhase/TurnEnd 安全点存档，首版不承诺跨版本回放；交互事件等新增阶段需另行设计安全点。迁移后的存档仍需结构与不变量校验，不承诺维持旧版本结果。
- 备选：完整事件溯源、任意阶段存档、跨版本回放；当前成本超过收益。
- 复审条件：出现需要任意阶段恢复、玩家可观看回放或长期跨版本兼容的明确需求时重新评估。

## ADR-0007：R1/R2 采用简洁国风方向，写实立绘后置

- 状态：已接受
- 日期：2026-10-23
- 背景：`08-ui-design.md` 建议简洁国风战略桌面；旧 `ui-plan-ibaye.md`（原文件名 `Three_Kingdoms_Godot4_UI_Plan.md`）主张写实半身立绘/玄铁暗金，两者成本与范围不同；旧文件还基于 iBaye/原版规则，与 clean-room 冲突。
- 决策：R1/R2 采用 08 的方向（低饱和、墨色/纸本、通用头像/徽记）；写实半身立绘不作为当前阶段承诺，R2 后按样片/预算评估。旧 UI 计划归档到 `godot` 分支 `docs/reference/ui-plan-ibaye.md`，仅作历史/视觉参考，不作为实现依据。
- 后果：R1 美术成本可控；如果以后转写实，UI/美术规范和内容量需要重新评估。
- 复审条件：R2 试玩、预算或美术样片表明写实方向更合适。
