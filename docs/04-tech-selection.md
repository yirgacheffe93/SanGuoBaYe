# 04 · 技术选型（待决策）

> 当前状态：**未锁定，优先验证 C#**。最终选择需实际 spike 数据；对 ADR-0003 的后续决定新增 ADR，不覆盖历史记录。

## 1. 需求

| 需求 | 权重 | 说明 |
|---|---|---|
| 2D UI 能力强 | 高 | 大量面板、列表、地图、弹窗、中文排版 |
| 领域代码可维护 | 高 | 回合、命令、事件、AI、战斗，预计 2–5 万行 |
| 可测试 | 高 | 无头运行、单元测试、回放 |
| 迭代速度 | 中 | 内容/数值频繁调整 |
| 性能 | 中 | 回合制；AI/大战场需要可控 |
| macOS/Windows 导出 | 中 | 首发 macOS，后续 Windows |
| 生态/工具 | 中 | 调试、编辑器、资源管线 |
| 学习成本 | 低–中 | 单人/小团队，时间不着急但不能无限 |

## 2. 候选

### A. Godot 4 + GDScript

- 优点：与 Godot 集成最自然；迭代快；场景/信号/UI 写起来轻；社区大；导出简单。
- 缺点：虽支持静态类型标注，规则代码仍运行于 Godot；headless 不等于脱离引擎。大型工程的重构与测试体验需实测，不能仅按动态语言标签判断。
- 适合：单人、快速原型、UI 为主、规则规模可控。

### B. Godot 4 + C#

- 优点：静态类型、重构/测试工具成熟；适合复杂领域和 AI；性能更好；仍保留 Godot 的 2D/UI。
- 缺点：需要 .NET SDK；C# 导出模板/构建链更重；Godot 的 C# 生态/示例少于 GDScript；热重载体验略差。
- 适合：规则/AI 复杂、长期维护、团队有 C# 经验。

### C. Unity + C#

- 优点：C# 生态成熟；工具链完善；招聘容易。
- 缺点：2D UI/回合制不是它的强项；包体/许可/运行时复杂度；对一个 2D 策略游戏偏重。
- 适合：团队已有 Unity 经验、需要商业中间件。

### D. 自研 / Rust + Bevy / 其他

- 优点：完全可控；性能好。
- 缺点：UI、编辑器、导出、音频、输入全部自己造；对单人项目是巨大风险。
- 适合：引擎/工具链本身就是项目目标，或团队很强。

## 3. 评估矩阵（初始判断，1–5 分）

权重：UI 25%、领域维护/测试 25%、迭代 15%、性能 10%、导出 10%、生态 10%、学习 5%。

| 方案 | UI | 维护/测试 | 迭代 | 性能 | 导出 | 生态 | 学习 | 加权 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Godot + GDScript | 5 | 3 | 5 | 3 | 5 | 4 | 5 | **4.20** |
| Godot + C# | 5 | 5 | 3 | 4 | 4 | 4 | 3 | **4.30** |
| Unity + C# | 4 | 5 | 3 | 4 | 4 | 5 | 3 | **4.15** |
| Rust/Bevy 自研 | 2 | 4 | 2 | 5 | 3 | 2 | 1 | 2.85 |

> 分数是主观初始值；spike 后按实际体验修正。

硬约束先于加权评分：当前要求规则测试在未安装 Godot 时运行，GDScript 不满足这一要求。若改选它，需新增 ADR，将验收改为 Godot headless，并同步修改架构与路线图；不能用 4.20 与 4.30 的分差替代这一决策。

## 4. 初步分析

- **引擎**：Godot 4 是最合适的默认选择。2D/UI 强、开源、macOS 导出简单、包体小；Unity 对这个项目偏重，自研风险过高。
- **语言**：
  - 如果规则/AI 会长期演进、且你熟悉 C#，选 **C#**：静态类型和测试工具对 2–5 万行的领域代码很重要。
  - 如果更看重快速迭代、单人开发、不想维护 .NET 构建链，可评估 **GDScript**：先明确接受 headless 替代独立运行，再坚持静态类型、模块边界和测试纪律。
  - 不建议“核心 C# + UI GDScript”混用作为默认方案；两种语言会增加构建、调试和团队协作成本。除非有明确收益，否则统一一种。
- **版本锁定**：spike 记录具体 Godot .NET 版本、兼容 .NET SDK、导出模板与目标架构，在同一组合上验证并锁定；不把“4.x / 8+”当可复现构建规格。
- **架构与迁移**：领域概念可复用，但跨语言仍需重写规则、序列化、测试与适配；分层降低迁移范围，不代表迁移低成本。

## 5. 推荐

**首选：Godot 4 + C#**（如果开发者接受 C# 和 .NET 工具链）。
**条件备选：Godot 4 + GDScript**（只有明确接受规则测试依赖 Godot 运行时后再考虑）。

理由：

- 这个项目的难点在规则、AI、战斗和数据管线，不在渲染；C# 的静态类型和测试工具更稳。
- Godot 仍然负责 UI/场景/输入/音频，不会失去 2D 开发效率。
- Domain/Application 使用不引用 Godot 的普通 .NET 类库；JSON/存档为适配层，Godot 仅负责 UI、输入与音频。先用实际测试验证边界。

**不推荐**：Unity（偏重）、自研引擎（成本/风险）、Electron/Web（不是这次重写的目标）。

## 6. Spike 计划（1–2 周）

目标：用最小代价验证语言/工具链，而不是做完整游戏。

### 任务

1. 优先建 Godot .NET UI 工程与独立规则类库；先验证 macOS 导出和纯 .NET 测试。如果工具链阻塞或迭代体验明显不合适，再做 GDScript 对照，不强制重复实现两个完整 spike。
2. 实现同一段领域逻辑：
   - `World` + `Turn` + `Command` + 一个城池命令（开发）
   - 一个战斗伤害公式（固定种子）
   - 一个 JSON 内容加载 + schema/引用校验
   - 安全点存读档，恢复 RNG 当前状态与待执行任务
   - 3–5 个单元测试
3. 做一个最小 UI：城池列表 + 详情 + 执行命令 + 任务队列 + 回合报告；按 `08-ui-design.md` 验证不可用原因、取消与成本显示。
4. 记录：
   - 代码量/重复代码
   - 测试运行速度/调试体验
   - UI 绑定/数据刷新方式
   - 构建/导出时间、包体
   - 你对迭代速度的主观感受
5. 新增 ADR，完成对 ADR-0003 提议的最终选择，记录语言/具体版本/工具链、结果和风险。

### 验收

- 首选方案跑通“加载内容 → 执行命令 → 回合推进 → UI 刷新 → 存读档”；启用备选时对照验证同一条流程。
- 能在 macOS 导出/运行。
- C# 规则测试通过普通 .NET 测试运行器执行，不引用 Godot.NET.Sdk 或 GodotSharp；UI 冒烟测试单独运行。备选 GDScript 使用 Godot headless，需记录需求变更。
- 连续执行与存读档后继续执行得到相同状态；预览不会改变 RNG。
- 有明确的“选 A 不选 B”的理由，而不是“感觉”。
