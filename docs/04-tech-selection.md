# 04 · 技术选型（待决策）

> 当前状态：**未锁定**。本文给出需求、候选、评估矩阵和 spike 计划。最终选择写成 ADR-0003。

## 1. 需求

| 需求 | 权重 | 说明 |
|---|---|---|
| 2D UI 能力强 | 高 | 大量面板、列表、地图、弹窗、中文排版 |
| 领域代码可维护 | 高 | 回合、命令、事件、AI、战斗，预计 2–5 万行 |
| 可测试 | 高 | 无头运行、单元测试、回放 |
| 迭代速度 | 中 | 内容/数值频繁调整 |
| 性能 | 中 | 回合制；AI/大战场需要可控 |
| macOS/Windows 导出 | 中 | 首发 macOS，后续 Windows |
| 生态/工具 | 中 | 调试、编辑器、资源管线 |
| 学习成本 | 低–中 | 单人/小团队，时间不着急但不能无限 |

## 2. 候选

### A. Godot 4 + GDScript

- 优点：与 Godot 集成最自然；迭代快；场景/信号/UI 写起来轻；社区大；导出简单。
- 缺点：动态类型，大型领域代码容易失控；测试/重构工具弱于 C#；AI/战斗模拟性能一般。
- 适合：单人、快速原型、UI 为主、规则规模可控。

### B. Godot 4 + C#

- 优点：静态类型、重构/测试工具成熟；适合复杂领域和 AI；性能更好；仍保留 Godot 的 2D/UI。
- 缺点：需要 .NET SDK；C# 导出模板/构建链更重；Godot 的 C# 生态/示例少于 GDScript；热重载体验略差。
- 适合：规则/AI 复杂、长期维护、团队有 C# 经验。

### C. Unity + C#

- 优点：C# 生态成熟；工具链完善；招聘容易。
- 缺点：2D UI/回合制不是它的强项；包体/许可/运行时复杂度；对一个 2D 策略游戏偏重。
- 适合：团队已有 Unity 经验、需要商业中间件。

### D. 自研 / Rust + Bevy / 其他

- 优点：完全可控；性能好。
- 缺点：UI、编辑器、导出、音频、输入全部自己造；对单人项目是巨大风险。
- 适合：引擎/工具链本身就是项目目标，或团队很强。

## 3. 评估矩阵（初始判断，1–5 分）

权重：UI 25%、领域维护/测试 25%、迭代 15%、性能 10%、导出 10%、生态 10%、学习 5%。

| 方案 | UI | 维护/测试 | 迭代 | 性能 | 导出 | 生态 | 学习 | 加权 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Godot + GDScript | 5 | 3 | 5 | 3 | 5 | 4 | 5 | **4.20** |
| Godot + C# | 5 | 5 | 3 | 4 | 4 | 4 | 3 | **4.30** |
| Unity + C# | 4 | 5 | 3 | 4 | 4 | 5 | 3 | **4.15** |
| Rust/Bevy 自研 | 2 | 4 | 2 | 5 | 3 | 2 | 1 | 2.85 |

> 分数是主观初始值；spike 后按实际体验修正。

## 4. 初步分析

- **引擎**：Godot 4 是最合适的默认选择。2D/UI 强、开源、macOS 导出简单、包体小；Unity 对这个项目偏重，自研风险过高。
- **语言**：
  - 如果规则/AI 会长期演进、且你熟悉 C#，选 **C#**：静态类型和测试工具对 2–5 万行的领域代码很重要。
  - 如果更看重快速迭代、单人开发、不想维护 .NET 构建链，选 **GDScript**：但必须强制静态类型、模块边界和测试纪律。
  - 不建议“核心 C# + UI GDScript”混用作为默认方案；两种语言会增加构建、调试和团队协作成本。除非有明确收益，否则统一一种。
- **Godot 版本**：4.x 稳定版；如果选 C#，用 .NET 8+ 的 Godot .NET 版本。
- **架构不绑定语言**：`02-architecture.md` 的领域模型/命令/事件设计对两种语言都适用，spike 后可以替换实现。

## 5. 推荐

**首选：Godot 4 + C#**（如果开发者接受 C# 和 .NET 工具链）。
**次选：Godot 4 + GDScript**（如果优先单人快速迭代、或对 C# 不熟）。

理由：

- 这个项目的难点在规则、AI、战斗和数据管线，不在渲染；C# 的静态类型和测试工具更稳。
- Godot 仍然负责 UI/场景/输入/音频，不会失去 2D 开发效率。
- 若后续发现 C# 构建/导出成本过高，Domain 层可以按接口迁移到 GDScript；架构设计已经隔离了引擎。

**不推荐**：Unity（偏重）、自研引擎（成本/风险）、Electron/Web（不是这次重写的目标）。

## 6. Spike 计划（1–2 周）

目标：用最小代价验证语言/工具链，而不是做完整游戏。

### 任务

1. 建一个空 Godot 4 工程（两个版本各一份，或同一工程切换）。
2. 实现同一段领域逻辑：
   - `World` + `Turn` + `Command` + 一个城池命令（开发）
   - 一个战斗伤害公式（固定种子）
   - 一个 JSON 内容加载 + schema 校验
   - 3–5 个单元测试
3. 做一个最小 UI：城池列表 + 详情 + 执行命令 + 回合推进。
4. 记录：
   - 代码量/重复代码
   - 测试运行速度/调试体验
   - UI 绑定/数据刷新方式
   - 构建/导出时间、包体
   - 你对迭代速度的主观感受
5. 写 ADR-0003：选择语言/版本/工具链，记录理由和风险。

### 验收

- 两个 spike 都能跑通“加载内容 → 执行命令 → 回合推进 → UI 刷新”。
- 能在 macOS 导出/运行。
- 能在命令行跑测试。
- 有明确的“选 A 不选 B”的理由，而不是“感觉”。
