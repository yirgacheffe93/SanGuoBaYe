# 19 · 道具发现位定位与修复方案

> 状态：取证与定位已完成，规则及导入修复待实施。2026-10-26 原始生产 WASM 证据确认读取 U8 字节视图造成误判，详见 `20-setgoods-diagnosis-result.md`。以下保留原设计，便于按修复与验收步骤继续；其中真实条件、初始队列和重复项的旧证据以新诊断为准。

## 1. 建议结论

先修正生产采样的完成判定，再定位写入；确认根因后只实施一套确定的规则。当前不直接把 `entry.Discovered = true` 加进搜寻，也不新增兼容模式或第二份“已发现道具”状态。

优先验证报告等待造成的提前采样。这是有源码依据的假设，尚不是根因：

1. `.reference/source` 当前为 `3f0e168`。其 `citycmd.c` 道具成功路径先调用 `ShowGReport`，返回后才调用 `SetGoods`。
2. `ShowGReport` 调用 `GamDelay(300, 2)`；`GamDelay` 通过消息循环等待计时器或有效按键、触摸消息。
3. 生产 `baye.js` 包含 Asyncify 和 `emscripten_sleep`。WASM 导出函数返回到 JS 的时刻可能只是让出执行权，需要验证实际调用链。
4. 道具候选选定以后，该成功路径没有额外 `gam_rand()` 调用。因此候选选定、报告等待中、发现位写入后，可以具有相同 RNG 状态。

这意味着现有“随机数正确、报告已显示”的证据不足以证明命令已经完成，也暂不足以证明生产漏写发现位。

## 2. 本次代码检查发现的验证缺口

| 位置 | 已核实事实 | 处理建议 |
|---|---|---|
| `MainSearchRules.ExecuteToolSearch` | 条件通过后只生成报告，没有写发现位 | 根因确定后在规则层统一提交变化 |
| `MainSearchTests.LoadContent` | 将全部人物/道具条件重置为零，并由 `ToolIds` 重建未发现队列 | 拆分真实内容加载和显式构造场景；生产 golden 测试必须使用真实内容 |
| `Tool_search_preserves_observed_production_queue` | 固定断言 `Discovered=false`，没有证明生产采样的完成阶段 | 保留原始观察记录；重新采样后再确定最终回归断言 |
| `golden-m2b.json` | 道具样本记录最终 RNG 和发现位，缺少完成阶段、调用完成证据、读取地址 | 使用独立诊断记录补齐，确认后更新正式 golden |
| `MainCity.ToolIds/ToolEntries` | 两套表示同时存在，只有后者保存发现位 | 本次所有候选、状态写入、断言使用 `ToolEntries`；`ToolIds` 继续仅承担已有兼容用途 |

实际 JSON 中，190 年 `tool-000` 和 `tool-031` 的 `bole` 都为 0，北平初始队列确为未发现的 `tool-031`。所以静态条件对这两个样本没有阻拦；运行时仍需记录实际加载的条件，以排除加载或索引差异。

## 3. 第一阶段：补齐生产采样完成条件

新增独立离线工具 `tools/main-import/diagnose-setgoods.mjs`，复用现有 VM/bridge 加载方式，但使用能够推进执行的定时器和消息驱动。现有导入器关闭定时器是其静态加载策略，不能原样用于需要等待的命令流程，也不能据此认定此前 golden 使用了相同驱动。

先运行未经修改的生产 WASM，固定库、bridge、JS、WASM 的 SHA-256 和 main commit；每个场景从独立初始化状态开始。保留两个既有场景，增加“同一执行者为非玩家势力”的诊断对照，以区分报告等待路径；该对照不代替真实玩家场景。

按语义阶段采样，不使用固定等待若干毫秒作为完成判定：

| 阶段 | 采样点 | 用途 |
|---|---|---|
| S0 | 命令接受前 | 初始条件和城市队列 |
| S1 | 接受后、执行前 | 命令原始槽位、执行者离城、执行前 RNG |
| S2 | 发现报告可见、报告等待中 | 检验现有观察是否只是中间状态 |
| S3 | 报告关闭、搜寻处理返回后 | 判断发现位是否真正提交 |
| S4 | 对应命令槽清空、人物归队，月度更新前 | 形成命令级 golden 的稳定边界 |
| S5 | 月度更新后、保存并重新加载后 | 判断是否存在后续覆盖和持久化问题 |

每个阶段记录：城市原始索引、`ToolQueue/Tools`、队列原始 U16、反射数组基址与元素宽度、原始内存字节、RNG、命令槽、人物位置及当前等待状态。golden 中的数组必须复制成数值快照，不保存会随后变化的反射对象或内存视图。

若是一次性命令导出，等待 Asyncify 完整完成；若驱动的是持续运行的主循环，等待对应命令的 S4 条件，不能等待整个游戏退出。`Asyncify.state == Normal` 单独不足以证明完成，还要检查是否有挂起 continuation，并结合命令完成条件。运行时不暴露这些字段时，以可观测的阶段事件和命令状态组合判定，明确记录证据限制。

采样期间只关闭报告或推进其必要等待，不额外触发下一条命令。设置超时；超时输出最后阶段和挂起信息，样本标为未完成，不写入正式 golden。日志、采样和输入驱动不得自行调用游戏 RNG。

**第一阶段退出条件：** 两个原始场景均取得 S4 快照，或者产出能定位卡在哪个等待点的失败记录。如果 S4 已设置高位，直接进入规则修复，不必先重编译 C 做全面插桩。

## 4. 第二阶段：必要时定位写入链

仅当生产 S4 仍未写入时，沿调用链取证：

1. 在条件判断处记录候选原始 ID、`count`、条件资源/时期、`fo`、执行者索引、城市索引，确认是否通过条件。
2. 记录报告进入和退出事件，确认返回后确实到达 `SetGoods`。
3. 在 `SetGoods` 入口记录 `city/goods/ToolQueue/Tools`，每次循环记录 `i`、原始值、比较结果、写入地址和前后值。
4. 对照生产读取地址，明确元素寻址为“基址 + 元素索引 × 元素宽度”；用原始字节和反射值交叉验证。内存增长后重新获取 HEAP 视图。
5. 若写入成功但 S4/S5 变回原值，追踪该地址后续写入、队列移动、时期加载和恢复行为。

先检查生产导出和现有调试能力，不假定 `_SetGoods` 可以从 JS 直接调用。若未导出，只在独立诊断构建中增加入口，分别测试直接调用、完整搜寻路径和报告禁用对照。

诊断构建单独记录源码 commit、构建参数和产物 hash。重新编译的 C 插桩只能解释源码路径，不能单独证明原始生产二进制行为；最终结论必须回到未经修改的生产 WASM 完整流程验证。不要通过替换 JS 中的同名函数就假定截获了 WASM 内部直接调用。

| 实验结果 | 根因归类 | 对应处理 |
|---|---|---|
| S2 未发现，S3/S4 已发现 | 采样早于提交 | 修 golden 驱动和 C# 发现位提交 |
| 原始内存已变，反射值未变或读取地址不同 | 观测或映射错误 | 修读取器，重新生成受影响证据 |
| 条件未通过或候选索引不符 | 条件、资源或调用映射问题 | 修正确认有误的一层，重新验证报告和 RNG |
| 写后被覆盖 | 后续流程覆盖 | 找到第一处覆盖；区分正常规则和缺陷，决定修复位置 |
| 完整执行、地址正确、条件通过，生产仍不写 | 生产行为与源码预期存在差异 | 记录证据，明确选择严格复现或修复原版缺陷 |

若最后一种结果成立，本方案建议把防重复搜寻作为有意的缺陷修复，单独记录行为决策和修复后的规则测试；生产原始 golden 继续记录不写入的事实。不能把修复行为改写成“生产本来如此”。

## 5. 确认后的 C# 规则设计

继续使用城市中的 `MainCityToolEntry.Discovered` 作为唯一发现状态，保持当前领域结构。发现不是装备或出队，不删除队列项，不改人物装备，不按全局 ToolId 去重。

严格保留现有执行顺序：构造有序未发现候选 → 按原次数消耗 RNG 选择 → 校验伯乐 → 提交发现位 → 返回成功报告。失败和空候选不修改状态，不补抽候选。报告由 `MainOrderExecutor` 在规则返回后发布。

需要特别保留重复项语义：同源 C 候选列表返回道具 ID，`SetGoods(city, goods)` 标记该城市**第一个同 ID 且未发现的队列项**，未必是随机选中的那个物理槽位。不能仅因为 C# 保留了对象引用，就直接标记随机选中的 `entry`。

可在 `MainSearchRules` 内增加小型私有方法，避免本次引入通用道具服务：

```text
TryMarkFirstUndiscovered(city, toolId):
    按 ToolEntries 原顺序查找第一个 ToolId 匹配且 Discovered=false 的项
    找不到：返回 false
    找到：设置 Discovered=true，返回 true
```

候选已经选中且条件通过，正常情况下提交应当成功。若失败，视为状态一致性错误，不发布成功报告，按项目现有异常方式暴露问题，不静默伪造“无收获”。此提交方法不消费 RNG。

提交与报告在 C# 中顺序执行；UI 只消费提交后的报告，不把状态修改放进报告弹窗关闭回调。生产报告前后的等待是取证阶段边界，C# 不必复制它的阻塞式 UI 结构。

## 6. 回归与验收

先分开两类测试数据：`LoadProductionContent()` 保留真实条件、高位、顺序；受控分支测试显式设置自己需要的场景数据。不要在所有测试共用的加载方法中重置全部条件。

| 用例 | 必须验证 |
|---|---|
| 原始场景 A / B | 依据重新采样的 S4 golden 验证发现位、RNG、资源、归队和清槽；A 的注入步骤完整记录 |
| 玩家报告等待对照 | S2 与 S4 各自的队列值；证明测试断言使用完成后的阶段 |
| 同一队列项再次搜寻 | 已发现项不再成为候选；空候选时不消费候选选择 RNG |
| 同城重复道具 | 选中后一个同 ID 候选时仍标记第一个未发现同 ID 项；下一次只消费剩余实例 |
| 已发现与未发现混排 | 跳过已发现项，剩余候选顺序不变 |
| 两城相同道具 | 只修改目标城市的一个队列项 |
| 伯乐匹配 / 不匹配 | 匹配可提交；不匹配不写、不重抽、不报成功 |
| 空候选 | 无发现、不访问不存在的条件、不增加候选 RNG 调用 |
| 存读档连续性 | 发现后保存重载，队列状态不丢失；后续搜寻与未中断会话一致 |
| 内容隔离 | 一个 Session 发现后，不改变静态 Period，也不影响新 Session |

重复项的精确槽位行为若尚无生产 golden，先作为同源 C 规则测试标注来源，不把受控 C# 用例称作生产验证。

存档本次不新增字段，继续使用 schema 4；旧档已有的布尔值如实保留，不能根据报告文本或全局道具 ID 推断曾经发现过的实例。修复生效后从当前状态继续执行，不承诺恢复旧档中未持久化的历史发现。若最终需要同时支持多套规则，再另行设计并持久化规则版本，不能挪用 `RngAlgorithmVersion` 表达发现位策略。
